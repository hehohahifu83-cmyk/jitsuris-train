# G3 金額の不明原因の見直し（2026-11-14 Codex）

対象：jitsuris-train `1ebfa7d`（原因調査のcommit 699a6fbを含む）、ai-bridge `ad6691f`。実装P・新しい本体予測・本体学習・確定ラベルの変更は行わない。

## 数の読みで先に訂正する点

保存JSONの再集計ではamount270判定中153がunknown、amount_without_cueは100、そのうち4表が92という集計を確認した。92の内訳はt012=17、t022=24、t062=21、t098=30（種子3本の合計）。

ただし4表が全部「州の名前の列」という説明は誤り。t098の10列はAnnual/Monthly Income、GAINS/RRAG、OAS/GISなど所得・給付額の列である。ここは「金額の意味の情報がない」のではなく、「現在のcue辞書にその英語・仏語や給付の略語がない」と区別すべき。t022にもFarmCashReceiptTypeという列名、t012のValueTypeにはdollars、t062のTypeにはCapital expendituresという値があり、情報の所在が違う。現行ルールがその情報を使わないことと、その情報が存在しないことは別。

現行amount_without_cueの安全条件は残す意見に賛成。数の大きさや隣の数値の大きさから金額を推測して例外にしない。将来、Income・給付名の限定語彙、明示的な単位/指標の値、確実に対応付けられた表題を使うなら、Pとは別の変更として事前記録・反例・新しい陣で確かめる。時点/区域/識別子へ単位が漏れない制約も要る。

## amount_precision の18判定を全部誤検知にしない

precisionに実際に入るのは再確認用のvalues5。検査役や末尾の通貨判定が使うvalues全体とは違うので、両方を混ぜて数えない。

| 列ID | 現行precisionが引っかかる値の性質 | Pの候補としての扱い |
|---|---|---|
| g3-0063・0261 | 通貨記号つき整数の3桁区切り | 正しい区切りを認識する候補：2列×3本=6判定 |
| g3-0481・0485・0743 | セント単位への差が、ごく小さい浮動小数誤差と整合 | 候補：3列×3本=9判定。元データが本来2桁だったという証明ではない |
| g3-0480 | values5に本当に長い精度が残る | 停止を維持：1列×3本=3判定 |

よって18は停止した合計で、緩和の検討対象は最大15判定（5列×3本）。Pで15が最終的に正答へ戻るかは、検査役・rho・辞書・末尾の通貨チェックを通して測らなければ言えない。

`numeric_probe.py` は現行の停止、通貨のある本当の小数、区切りの後ろに小数がある値、桁区切りの不正な形、コードとの手がかり衝突、非常に大きい数の誤差許容が広がり過ぎないことを11項目で検査した。値は出力に転記しない。実データの分類結果はnumeric_probe_result.json。

2ULPかつ絶対差1e-8以下という数値の点検を使ったが、これは表現誤差との整合性を見るレビュー用の目安で、採用するPの閾値を決めたものではない。

## Pの範囲への意見

- カンマをすべて除去せず、通貨・ロケールの根拠と整合する厳密な3桁区切りだけを認識する。小数カンマ、欧州式、誤った区切り、指数表記、負数/括弧、欠損について扱いを先に定義する。
- 通貨記号があるというだけでprecisionを無条件に通さない。真に3桁以上の小数を持つ金額は止めたままにする。
- すべての値の2桁丸めや、値の大きさに比例する緩い許容を使わない。Decimalによる差と厳しい絶対上限等で表現の揺れだけに限定し、原値を上書きしない。混合列では1件でも真の高精度値が残れば止める。
- amount_without_cue、手がかり衝突、period_header、検査役、rho、辞書を同時に変更しない。通る可能性と安全の根拠を分離する。
- 教材14バッチ、F1・G1・G2で重大非増を確認する方針に賛成。ただしそれらは使い済みの回帰点検であり、そこを繰り返して合わせ込んだことを新しい性能の証拠にはしない。変更した全列の内訳、重大以外の悪化、unknown/除外列での根拠のない断定も記録する。
- G3は原因の発見用。採否をまだ使っていない別の陣で測る方針に賛成。Pで直らないt051の本体の迷いや検査役の止めを、Pの効果として混ぜない。

## 同版の再現と stage() の問題

Python3.12.14・scikit-learn1.8.0・NumPy2.3.5・SciPy1.17.0、OMP/BLAS各1スレッドで、元のamount_unknown.pyを実行。元レポートを上書きしない一時出力で、588件のJSONが保存済みamount_unknown.jsonと完全一致した。採点関係のコードは調査commit699a6fbから現HEADまで差分なし。セット・確定ラベル・予測9本の由来検査も通過し、辞書SHAも独立に確認した。

同時に再確認→検査役→rho→辞書→末尾の通貨確認の各出力を直接記録した。元stage()はfinalと最初のguarded判定、途中段の理由だけを使うため、最後にunknownへ落ちた段を特定できない。最初に止めた理由と、最終結果を決めた段は区別する必要がある。

| 金額列の最後にunknownとなった段 | 3本の合計 |
|---|---:|
| 再確認 | 64 |
| 末尾の通貨の手がかり確認 | 74 |
| 検査役 | 6 |
| 本体・見張り | 9 |
| 不明合計 | 153 |

- 元のamount_without_cue 100のうち68は、再確認でunknown→rhoでamountへ復帰→末尾のamount_cue_vetoでunknown。残り32は最後も再確認段の停止である。100という理由タグの集計は再現するが、「再確認だけで決まった100件」とは言えない。
- g3-0728（Reimbursement、3本）は、再確認・検査役をamountで通り、末尾の通貨確認でunknown。元の「再確認が止めた（理由なし）」は誤った帰属。
- 見張りでunknownだった12件のうち3件も、rhoでamountへ戻った後に末尾の確認でunknown。最後の停止としては本体・見張り9件になる。
- 元の「本体・見張りで不明（理由なし）」12件について、保存予測の本当のguard理由はprobability_below_threshold 5・numeric_top2_too_close 6・other_class 1。final側の理由にないだけで、元のguard理由はある。

したがって、再確認の安全条件だけを外しても後段の74件は自動的には直らない。末尾の安全条件まで一緒に緩めるのはPの範囲外であり、賛成しない。原因の報告は「最初の停止」「復帰」「最後の停止」を分け、f[1]だけでなく末尾の判定理由も記録することを先に提案する。

trace.jsonは588判定の各段のラベル・理由・ID・種子のみ（元の値は転記しない）。summary.jsonは理由タグと最後の停止のクロス集計。replay.pyは元の関数を包むだけで、戻り値は変えない。合成1列でも辞書形式の検査役出力を含む経路を検査した。検査役は所定の14バッチで再構築した。本体モデルの学習ではない。

初回の追跡は検査役出力の辞書を配列として扱い途中終了した。修正と合成経路の確認後にやり直した成功実行を上記の再現結果とした。計測の失敗を元の研究コードの不具合とは扱っていない。
