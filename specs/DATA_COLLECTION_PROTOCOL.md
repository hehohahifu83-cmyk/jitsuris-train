# データ収集の手順（指示役 Claude、2026-10-21・v1）

実行役：ChatGPT（STATE.md の S8・S11・S12）。親文書：`specs/IMPROVEMENT_PLAN.md` 3.2〜3.5・第 5 章 WP-E。評価側の集め方は `SEALED_EVAL_PROTOCOL.md`。既存の仕組み：`materials/fetch_real.py`＋`materials/fetch.request`（Actions で集める）、`materials/real_corpus_*.jsonl`（ラベルなし）→ `real_labels_*.jsonl`（先生のラベル）、`select_next.py`（能動学習の選び方）、`data_inventory.py`（棚卸し）。

## 1. 何のために何を集めるか（問題 → データ）
| 問題（根拠は IMPROVEMENT_PLAN.md 第 3 章） | 足すデータ | 種類 |
|---|---|---|
| 金額↔数量の取り違えが重大の 14／16 | 単位が見出し・値・同じ表のどこかに書かれた金額と数量の対。「Value」「合計」「Total」など汎用の見出し。単位がどこにもない難例（LABEL_GUIDE の決め方で付く列だけ） | 実データ＋難例の合成 |
| category↔quantity（横持ち・符号化された回答） | 横持ち表（見出しが分類名で値が件数）、コード列＋名称列の対、回答コード 1〜5 の列 | 実データ（統計表） |
| other を other と言えない | 測定値・指標・座標・学名・指数の列を含む表 | 実データ |

| 日付の書式（和暦・四半期・時刻・期間）がモデルに少ない | 書式の多様な日付列を含む表 | 実データ |

## 2. 受け入れ条件（共通。1 つでも満たさない表は入れない）
- **ライセンス**：個別に原文で確認して `license`（識別子）と原文の URL を記録。許可：CC0・CC BY（2.1 JP／3.0／4.0）・PDL 1.0・政府標準利用規約（第 1.0／2.0 版）・OGL v3.0・Open Government Licence – Canada・米国政府の公開データ・Singapore Open Data Licence。**除外**：CC BY-NC／SA／ND、独自規約で機械学習や再配布を禁じるもの、条件不明、有償、ログインが要るもの、規約でスクレイピングを禁じるサイト。この文書の出典の例は**確認済みの保証ではない**（取り込み時に原文を読む）。
- **プライバシー**：個人の氏名・自宅の住所・電話・メール・生年月日・顔写真・患者／児童／生徒／福祉／納税者の個別の記録の列は、取らない（値も見出しも保存しない）。法人の名称・事業所の所在地は取ってよい。**電話・メールの実データは集めない**（形式だけを仕様由来で作る）。個人名の列も集めない（人名は仕様由来で作る）。`independent_eval/discover.py` の `TITLE_DENY`・`HEADER_DENY`・`sensitive_value` を、そのまま同じ強さで使う。
- **公開元の割り当て**：SEALED_EVAL_PROTOCOL.md 第 2 章の `pool()` が `train` の公開元だけ。割り当ては中身を見る前に。
- **重複**：URL の完全一致、（見出し＋先頭 5 値）の SHA-256 の一致は 1 つにする。同じ見出し集合の表は 1 公開元あたり 3 表まで（毎年版を並べない）。1 表あたり 10 列まで。1 公開元は全体の 3% まで。
- **保存するもの**：見出し、先頭 5 値（既存の `fetch_real.py` と同じ）、同じ表の列名（12 まで）、単位列の値。元の CSV は保存しない。
- **行をそろえた値（2026-10-21 19:58 追加。W3b「表の計算の整合」の教材のため）**：既存の `fetch_real.py` は列ごとに別々に値を無作為に選ぶので、同じ表の列どうしで行がそろわない（単価×数量＝金額などを学習できない）。S11 で新しく取る表は、**表ごとに同じ行**（空でない値が多い行から、種を固定して最大 20 行）を選び、各列にその行の値を同じ順で `row_values`（長さは全列で同じ。空は ""）として保存する。`values`（5 値）はこれまでどおり別に残す。個人情報の列は除外したうえで（第 2 章）、除外した列は `row_values` も持たない。行の番号（元の CSV の何行目か）は `row_index` に記録し、値そのものの再取得はしない。
- **記録（行ごと）**：`source`（`<系統>:<データセット ID>`。新しい系統は `jp3`・`world2`・`hard`・`spec`）、`table`、`publisher`（正規化名）、`pool`、`license`、`license_url`、`retrieved_at`、`language`、`header`、`values`、`context`、`unit`。仕様由来・合成の行には `synthetic: true` と `generator: "<ファイル>@<コミット SHA>"`。
- 出力先：`materials/real_corpus_<系統>.jsonl`（ラベルなし）→ 先生が付けて `materials/real_labels_<系統>.jsonl`（`label`・`teacher` つき）。

## 3. 実データの集め方（優先順。どれも `pool()` が `train` の公開元だけ）
入口の例は「探し方」で、確認済みの URL ではない。見つけた表は、公開元・ライセンス・列を `independent_eval/discover.py` と同じ作りの候補一覧（メタデータだけ）にしてから、採用を決める。

### 3.1 日本の財務・調達・契約・補助金・予算決算（最優先。account・org・amount・date・id・text・quantity・rate）
- 探し方：デジタル庁のデータカタログ（data.e-gov.go.jp）と自治体の CKAN／オープンデータカタログの検索で、語＝契約・調達・入札・落札・随意契約・支出・支払・補助金・交付・助成・委託・予算・決算・歳入・歳出・基金・指定管理・使用料・手数料・公有財産・物品。国の契約情報（各府省の公表）、行政事業レビューの公表データ、調達ポータルの公開情報も候補（規約は要確認）。
- 欲しい列：勘定科目に当たる「科目」「款・項・目・節」「費目」「事業名」、取引先「契約相手方」「落札者」「交付先」、金額「契約金額」「予定価格」「落札率」、日付「契約日」「交付決定日」、番号「契約番号」「整理番号」。
- 量：120 表・約 1,000 列（日本語 100%）。1 公開元 3 表まで → 公開元 40 以上。
- 注意：落札率（rate）、予定価格（amount）、契約方式（category）、摘要（text）を含む表を優先。

### 3.2 法人・事業者の公開名簿（org・id・address・date・category）
- 国税庁の法人番号公表サイトの公開データ（基本 3 情報。法人名・所在地・法人番号・更新年月日・法人種別）、官公庁が公表する事業者の一覧（許認可・登録・指定事業者の一覧のうち法人のもの）。個人事業主・個人名が混じるものは除く。
- 量：30 表・約 200 列。同じ見出しの表が続くので、見出しの種類を増やすための表（登録事業者・指定事業者・補助事業者の名簿）を優先。

### 3.3 統計表（横持ち・コード対・階層見出し。quantity・category・id・rate・other）
- 探し方：e-Stat（政府標準利用規約 第 2.0 版・CC BY 互換・商用可。機械学習への明文の規定はないので、`license` の備考に「機械学習の可否に明文なし」と書く）、自治体の統計（人口・世帯・事業所・農林水産・観光・医療・福祉の集計表）。
- 欲しい形：見出しが分類名（年齢階級・産業・診療科）で値が件数の**横持ち**、コード列（`C02345V03131` の形）＋名称列の**対**、回答コード（1〜5）の列、指数・指標の列（other）、階層見出し。
- 量：100 表・約 700 列（横持ち 100 表以上を含む）。
- 注意：年の見出しだけの数値列（単位も文脈もない）は LABEL_GUIDE v1.4 で unknown（学習に使わない）。表の題名はモデルに渡らないので、題名がないと決まらない列は入れない。

### 3.4 日本語以外の表（系統の偏りを減らす。全種類）
- 探し方：データカタログのうち英国・アイルランド・カナダ・オーストラリア**以外**（米国連邦、シンガポール、ニュージーランド、EU 各国、世界銀行、国連、英語圏以外の政府）。英語の業務データ（小売の取引明細、注文、請求）で CC BY／CC0 のもの。
- 量：60 表・約 450 列、公開元 20 以上。

### 3.5 実列で足りない稀少な種類
- 人名・電話・メール：実データは集めない（上記プライバシー）。商品：商品名の列（品名・メニュー・薬名・書名ではなく商品）を含む公開表（調達の「品名」、価格調査、メニュー表）から実列を足す（目標 60 列）。税区分：公開データにほぼない（消費税の区分を持つ表は事業者の会計出力に限られる）。仕様由来で作る（第 4 章）。

## 4. 仕様由来の教材（業務ソフトの入出力形式。person・product・tax_class・phone・email・account・org・amount・date・id・text）
### 4.1 目的
製品が扱う日本の業務 CSV の形式を、見出し（本物）と値（合成）で作る。LABEL_GUIDE の種類は**形式の仕様から決まる**ので、先生のラベルは要らない（`teacher: "spec"`）。
### 4.2 形式の候補（`pool("vendor:<名前>")` で割り当ててから中身を見る）
会計ソフト（弥生会計、freee 会計、マネーフォワード クラウド会計、勘定奉行、PCA 会計、TKC 、OBC）の仕訳・取引・補助科目・取引先・部門の入出力、請求書（Misoca、board、MF クラウド請求書）、売上・POS・EC（Square、Airペイ、スマレジ、Shopify、BASE、STORES、楽天市場、Amazon の注文レポート、Yahoo!ショッピング）、銀行・カード明細（主要行・カード会社のダウンロード形式）、給与・勤怠、在庫・会員・予約。各社の公式ヘルプ・仕様書にある「インポート形式」「CSV の項目」。
### 4.3 形式の記述（`specs_src/<vendor>/<format>.json`）
```
{"vendor": "...", "product": "...", "format": "...", "url": "<公式ページ>", "retrieved_at": "2026-10-2x",
 "terms_note": "列名と語彙の事実だけを記録。説明文・画面・見本ファイルは転載しない",
 "columns": [{"header": "...", "class": "<LABEL_GUIDE の種類>", "value_kind": "date_jp|amount_jpy|slip_no|company|person|product|memo|tax_class|account|dept|phone|email|category|..."}],
 "vocabularies": {"tax_class": ["..."], "account": ["..."]}}
```
- 語彙（勘定科目・税区分の名称）は公式の一覧にある事実だけ。表記ゆれ（全角半角・括弧・略称）は仕様の範囲で。
- 仕様が型を決められない列は `columns` に入れない。

### 4.4 値の生成（`spec_gen.py`。評価用は別ファイルの `pd_gen.py`）
- `gen.py` を import しない。語彙を `gen.py` から写さない（先頭に由来を書く）。種を固定、生成コードのコミット SHA を行に記録。
- 値の種類ごとの生成器：日付（西暦スラッシュ・ハイフン・和暦・Excel 風・曜日つき）、金額（桁区切り・△・円付き・小数）、番号（伝票・請求書・取引先コード）、法人名（株式会社〜・〜有限会社）、**人名（姓名の組み合わせ。実在の特定の個人を再現しない）**、商品名、摘要（短文）、税区分（公式語彙）、部門・補助科目、電話（形式だけの乱数）、メール（`example.com`・`example.jp` などの予約ドメイン）、区分。
- ノイズの層：空欄・欠損の印（`-` `…`）・末尾の空白・全角半角の混在・列順の入れ替え・同じ表の無関係な列・見出しの表記ゆれ（括弧つき単位、注記）。**ガード v10 の一覧とは別に、そのベンダーの出力例にある書式だけ**を使う。
- 量（第 1 ラウンド）：`train` に割り当てた形式（20〜40）× 6 変種（行数・列の取捨・ノイズ）。稀少な種類（person・product・tax_class・email・phone）の仕様由来の表は、種類ごとに 100 表以上。

## 5. 難例の作り方（hard。金額↔数量・日付の書式・横持ち）
- 実データを優先（第 3 章の表から、金額系と数量系の列が同じ表にあり、単位が見出し・値・単位列にあるものを選ぶ）。足りない分だけ `hardcases_gen.py`（`gen.py` を import しない）で合成：
  - 金額と数量の対：単位つきの値（`1,200円`、`12個`）、単位なしで見出しだけ違う（`Amount` と `Quantity`）、汎用の見出し（`Value` ＋ 単位列、`合計`）、桁が同じ整数でも意味が違う列。
  - 日付の書式：和暦、四半期、時刻、期間、曜日つき、月名だけ（ガード v10 とは独立に、モデルが書式に頼れるようにする）。
  - 横持ち：見出しが分類名、値が件数。
- 量：1,200 列（実データ 600＋合成 600）。合成の行には `synthetic: true`。
- **LABEL_GUIDE が決められない難例は入れない**（unknown になる列を教材にしない）。

## 6. ラベル付け（費用を抑えながら誤りを増やさない）
1. 実データの列（第 3 章）：先生 1＝ChatGPT が LABEL_GUIDE v1.5 だけを根拠に全列へラベルを付ける（`teacher: "chatgpt-<日付>"`）。S（空・崩れた表）と unknown（決められない）を使う。
2. 現行のモデル（E5-base 版 31、CPU で `evaluate_checkpoint.py` か Kaggle）の予測と比べる。**一致した列は採用**。**不一致の列は Claude が裁定**（LABEL_GUIDE だけが根拠。理由の節を記録）。
3. 抜き取り：一致した列の 10% を Claude が確認する。先生の誤り率が 5% を超えたら、一致した列も全件確認する。
4. Claude の裁定は 1 ラウンド 500 列まで（超えたら、稀少な種類・金額↔数量・日本語を優先して残りは次のラウンド）。
5. 先生の 2 人が食い違い、LABEL_GUIDE が決められない列は教材に入れない。決め方を足したくなったら `LP` 番号で記録（ガイドは S6 の判定後に Claude が改訂）。
6. 仕様由来・合成は先生のラベルなし（構成時に確定）。Claude が 5% を無作為に確認して、仕様の読み違いを探す。

## 7. 学習への入れ方（`encoder_exp.py`）
- 新しい系統ごとに、`real_train_rows_with_units(...)` を使って行を足す。倍率と表あたりの上限は系統ごとに決めて、`FINETUNE_RESULTS.md` と HANDOFF に書く。系統の名前＝`source` の接頭辞（`jp3` `world2` `hard` `spec`）。合成の行（`synthetic: true`）は、別の環境変数（例：`FT_SYN_WEIGHT`）で重みを下げられるようにする（合成の比率が増えすぎないように。現在 19%）。
- 英国・アイルランド系（datagov_uk・datagov_uk2・ireland）の重み：`data_inventory.py` の「最大の系統」が各種類で 15% 以下になるまで、表あたりの上限を下げるか、系統ごとの行数の上限を設ける（これも一要因ずつ）。
- 比較は一度に 1 要因：(a) +jp3、(b) +spec、(c) +hard、(d) +world2、(e) 系統の上限。Kaggle の `FT_VAL=1`（検証＝学習側の表の 1/8。未知見出し 255 行、誤差約 2 ポイント）で、E5-base・学習率 3e-5・種子 2 つ。**差が 1.5 ポイント未満は差なし**。採否の規則は事前に書く（未知見出し macro-F1 → 重大 → 誤断定 → 不明）。複数を合わせた最終は、独立評価の候補として事前登録する。
- 固定試験で重大な取り違えが増えていないかを回帰診断として見る（採否の規則には使わない）。増えたら原因を調べる。
- 学習曲線（S12、`FT_REAL_FRAC`）の結果で、データの量を増やす価値が残っているかを先に確かめる（第 8 章）。

## 9. 禁止
- 固定試験・主セット・封印セット・PD-1 の行、見出し、公開元を教材に使う。評価セットの誤りを見て教材を作る。
- `eval2`・`eval3`・`main` の公開元の表を学習に入れる。
- 個人の氏名・連絡先の列を保存する。電話・メールの実データを集める。
- ライセンスが確かめられない表を「後で確認する」として入れる。
- LABEL_GUIDE・既存の学習データを、S6 の判定の前に書き換える（新しい系統の追加はよい）。
- 未見セット（blind_set*、セット 3・5・7）を開く。
