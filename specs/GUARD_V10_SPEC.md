# ガード v10 仕様：読めない日付・数の書き方を、仕様から足す（指示役 Claude、2026-10-21・v1）

実行役：ChatGPT（STATE.md の S7）。親文書：`specs/IMPROVEMENT_PLAN.md` 3.1。

## 1. 目的と原則
- 目的：見張りが「値の形が読めない」ために、正しい答えを不明にしている損（E5-base で 1.27%、日付の規則だけで 0.72%）を、**重大な取り違えを増やさずに**減らす。
- 原則 1：規則は **表記の定義** と **学習側の元の列の集計** から作る。固定試験・主セット・封印セットの行から作らない（v9 は固定試験の失敗を見て作ったので成績が甘かった。同じ轍を踏まない）。
- 原則 2：**単調**：v9.1 が日付・数として受け入れた値と列は、v10 も受け入れる。見張りが厳しくなる方向の変更は、この仕様の範囲外。**加法的に読む**：規則の否定例は「その規則が新しく受け入れない」という意味で、v9.1 がすでに受け入れる値は、否定例に書いてあっても v10 は受け入れたまま（単調が優先。2026-10-21 裁定、第 8 章）。
- 原則 3：緩める規則ごとに、定義・肯定例・否定例・列の条件を持つ。肯定例だけの試験は不合格。
- 原則 4：Python が正本、JS（`column-ai.js`）は同じ結果になること。fixtures で一致を確かめる（既存の `guard_fixtures.json`・`guard_value_fixtures.json`・`make_guard_*.py`）。
- 注記：Claude は主セットの値を見てラベルを付けた。この仕様は主セットの記憶からは作っていない（根拠は第 2 章の学習側の集計と表記の定義だけ）が、念のため **v10 の判定は封印セット #2 で行う**。主セットでの v10 の成績は参考（事前登録の副次列）として並べる。

## 4. 規則に含めないもの（理由つき）
- L4 **数字だけの日付ラベル列**（`53`、月番号・週番号・時など。学習側の日付列の 4.0%）：値だけでは日付・数量・ID を区別できない。見張りで救わない。ラベル方針（LABEL_GUIDE）側の問題として、S6 の判定後に Claude が決める（暦の部品の整数を date にするか、category／quantity にするか）。
- 値の代わりの説明文（`…公表しない`）：正当な非数値。不明のままにする。
- `` など私用領域の文字が前にある数：文字化け。原則を作れない。
- D14（Excel の日付番号）：誤受理の危険が大きい。
